# 리딤코드(프로모션 코드) 연구 — 설치 유도용 정본
*작성 2026-09-23 · 대표 지시 「목적 유도가 아닌 설치 유도로, 플랫폼별로 어떻게 쓰는 게 좋을지 연구해 저장」*

---

## 0. 한 줄 요약

우리 앱은 **무료**다. 그래서 코드가 주는 것은 «앱»이 아니라 **«광고제거 구독 1개월»**이다.
따라서 흐름은 언제나 **설치 → 앱 안/스토어에서 코드 사용 → 한 달 광고 없음** 이고,
코드의 진짜 기능은 할인이 아니라 **«지금 깔아야 할 이유»를 만드는 것**이다.

---

## 1. 어디서 받는가 — 발급 경로와 한도 (실측/원문 기준)

| | 애플 App Store | 구글 Play |
|---|---|---|
| 이름 | **오퍼 코드(Offer Codes)** — 구독 전용 | **프로모션 코드(Promo codes)** |
| 위치 | App Store Connect → 해당 **구독** → Offer Codes | Play Console → 수익 창출 → **프로모션** → 프로모션 코드 |
| 비용 | **무료** | **무료** |
| 형태 | ①**일회용 코드**(CSV 로 대량 내려받음) ②**맞춤 코드**(사람이 읽는 한 문자열, 여러 명이 사용) | 일회용 코드(대량 생성) |
| 혜택 | 무료 기간 · 할인가 · 선불 기간 | 1회성 상품 또는 구독에 적용 |
| 사용처 | 앱 안(`presentCodeRedemptionSheet`) · App Store «코드 사용» · `apps.apple.com/redeem?ctx=offercodes&id=…&code=…` **URL** | Play 스토어 «코드 사용» · `play.google.com/redeem?code=…` URL |
| 만료 | 코드별 만료일 지정 가능 | 지정 가능 |

**우리 현황(2026-09-22 API 실측)**: 구독 `SIGNUM Pro Monthly`(`com.signumhq.app.pro.monthly`) **APPROVED**, 기존 오퍼코드 **0개**.
→ 즉시 발급 가능한 상태다.

### 결정적 차이 — «맞춤 코드»가 배포에 훨씬 강하다
애플의 **맞춤(custom) 코드**는 `SIGNUM30` 처럼 **사람이 읽고 타이핑할 수 있는 한 문자열**이고
**여러 명이 쓸 수 있다**. 일회용 코드는 한 명당 한 줄이라 «뿌리기»에 수작업이 든다.
→ **공개 게시물에는 맞춤 코드, 1:1 답장·DM 에는 일회용 코드**가 맞다.

## 2. ⛔ 넘으면 안 되는 선 (두 스토어 공통)

1. **별점·리뷰를 대가로 코드를 주면 안 된다.** 두 스토어 모두 «인센티브 리뷰»를 명문 금지하고
   계정 제재 사유로 본다. 「리뷰 써주면 코드 드립니다」는 절대 쓰지 않는다.
2. **재판매·경매 유도 금지.** 코드를 파는 행위를 유도하는 문구도 금지.
3. **레딧·Quora 본문 링크 금지선과 충돌하지 않게** — 이 두 곳은 코드 문자열만 쓰고 링크를 넣지 않는다.
4. 허용되는 것: **설치 기념 선착순**, **커뮤니티 감사**, **베타 참여 보상**, **기간 한정 무료 체험**.

---

## 3. 「다음 사람을 위해 댓글 남겨주세요」 방식 — 왜 이게 강한가

대표가 지적한 그 방식이다. 배포자가 코드 N개를 공개로 뿌리고
**「쓰신 분은 «사용함» 이라고 댓글 달아주세요」** 라고 요청하는 형태.

작동 원리 세 가지:
- **댓글이 곧 도달이다.** 대부분 플랫폼(레딧·스레드·X·note)은 댓글 수·최근 댓글을
  랭킹 신호로 쓴다. 코드 배포는 «댓글을 만들 정당한 이유»를 준다.
- **사회적 증거가 쌓인다.** 「3번 썼습니다」 「감사합니다」가 달리면
  글 자체가 «진짜 사람이 쓰는 앱»이라는 증거가 된다. 광고문구 100줄보다 강하다.
- **소진 상태가 공개된다.** 남은 개수를 사람들이 서로 알려주므로
  «늦으면 못 받는다»는 압박이 자연스럽게 생긴다(우리가 만들지 않아도).

**설계 규칙**:
- 한 게시물에 **맞춤 코드 1개 + 사용 한도**(예: 선착순 50) 가 가장 깔끔하다.
  일회용 코드 여러 줄을 공개로 붙이면 봇이 즉시 쓸어간다.
- 「사용하셨으면 댓글로 알려주세요」는 **요청**이지 **조건이 아니어야 한다**
  (조건을 달면 인센티브 규정에 가까워진다).
- 남은 수량을 **우리가 주기적으로 갱신**해 댓글로 적는다 → 글이 계속 위로 올라온다.

## 4. 플랫폼별 전략 — 유입 기대치 순

우리 21일 실측 클릭(홈 398 · SEO 143 · bluesky 86 · quora 57 · x_us 45 · IH 27 · medium 23)을
«코드가 얼마나 먹히는가»로 다시 정렬하면 순서가 달라진다. 코드는 **커뮤니티형**에서 강하고
**검색형**에서 약하다(검색 유입은 코드 만료 뒤에도 계속 들어오는데 글에 죽은 코드가 남는다).

| 순위 | 플랫폼 | 왜 | 어떻게 |
|---|---|---|---|
| **1** | **Reddit** (r/thetagang·r/algotrading·r/stocks) | 팔로워 0이어도 도달하고 **댓글 문화가 가장 강하다**. 「코드 남았나요?」가 자연스럽다 | 서브 규칙 확인 필수(자기홍보 금지 서브 다수). **댓글이 아니라 «글»로** 올리되 링크 없이 코드 문자열만. 소진 갱신을 댓글로 |
| **2** | **IndieHackers** | 빌더 커뮤니티라 «만든 사람이 주는 것»에 호의적. 우리 글에 27댓글이 달린 전례 | 제품 업데이트 글 말미에 「IH 분들께 30장」 |
| **3** | **Bluesky** | 우리 건당 1위(10.2). 링크 벌점 없음·시간순이라 재게시가 먹힌다 | 코드 + 앱 실화면 이미지. 소진되면 인용글로 갱신 |
| **4** | **Threads / X** | 도달은 팔로워 의존이지만 **인용·답글이 붙으면 증폭** | 「댓글로 사용 보고」 방식이 가장 잘 맞는 형태 |
| **5** | **note(JP)** | 일본은 «無料コード» 반응이 좋고 기사 체류가 길다 | 기사 말미 고정 블록. 일본어 안내 필수 |
| **6** | **Quora / Medium / 블로그** | **비추천.** 검색 유입이 몇 달 이어지는데 코드는 한 달 뒤 죽는다 → «만료된 코드» 글이 남아 신뢰를 깎는다 | 쓰려면 «기간 명시 + 만료 후 문구 교체»를 전제로만 |

## 5. 수량 설계 (대표 지시: 「가능한 수량을 정해서 일정 수량을 여기저기 뿌리자」)

원칙: **한 번에 다 뿌리지 않는다.** 소진이 눈에 보여야 압박이 생기고, 남으면 김이 빠진다.

제안 — **1차 200장**을 이렇게 나눈다:

| 배포처 | 수량 | 형태 |
|---|---|---|
| Reddit 글 2건 | 각 40 | 맞춤 코드 1개 + 한도 40 |
| IndieHackers | 30 | 맞춤 코드 |
| Bluesky | 30 | 맞춤 코드 + 앱 화면 |
| Threads / X | 각 20 | 맞춤 코드 |
| note(JP) | 20 | 맞춤 코드 |
| 예비(1:1 답장·DM) | 20 | 일회용 코드 |

**운영 규칙**
- 유효기간 **30일**. 만료일을 게시물에 **명시**한다(만료 뒤 문구를 바꾸기 위해).
- 소진율을 **매 사이클 확인**하고, 70% 넘으면 그 채널에 2차를 준다(이긴 채널 키우기).
- **한 채널이 다 먹으면 그 채널이 이긴 것**이다 — 다음엔 거기에 몰아준다.
- 소진 0인 채널은 **문구가 문제인지 채널이 문제인지**를 가른다(같은 코드를 다른 문구로 재시도).

## 6. 측정 — 「몇 명이 깔았나」를 어떻게 아는가

⚠ 코드 사용은 **스토어에서 일어나므로 우리 클릭 카운터에 안 잡힌다.** 그래서 따로 봐야 한다.
- **애플**: ASC → 해당 구독 → Offer Codes 에 **사용 수(redemptions)** 가 뜬다.
- **Play**: Play Console → 프로모션 → 코드별 사용 현황.
- **채널 구분**: 채널마다 **맞춤 코드 문자열을 다르게** 만든다(`SIGNUMRD`·`SIGNUMIH`·`SIGNUMBS`…).
  그러면 사용 수만 봐도 **어느 채널이 설치를 만들었는지** 알 수 있다. 이게 코드의 숨은 장점이다 —
  링크 클릭이 아니라 **«설치 후 행동»을 채널별로 세는 유일한 수단**이다.

- 구독 APPROVED · 오퍼코드 **0개** → 발급만 하면 된다.

# ★ 2026-09-23 전면 실측 (대표 지시: 「추측말고 실측으로해」)

위 1~7절은 «조사»였다. 아래는 **실제로 API 를 두드리고 콘솔을 열어 확인한 것**만 적는다.
추측이었다가 실측으로 뒤집힌 것은 ⚠ 로 표시한다.

## A. 애플 — 두 가지가 «따로» 있다 (이걸 구분 안 하고 있었다)

### A-1. 앱 프로모션 코드 — **지금 100장이 놀고 있다**
ASC → 앱 → 성장 및 마케팅 → **프로모션 코드 → 코드 생성** 화면 실측 문구:

> SIGNUM HQ: Stock Market AI · 1.9.2 · iOS · **100개의 코드 남음**

- **버전당 100장, 무료, 이미 발급 가능 상태**다. 무료 앱이라 「깔 수 있게 해주는」 값어치는 없다.
- 그런데 **쓸 곳이 하나 있다**: MacRumors 개발자 포럼 **136번 스레드는 «프로모코드 전용»**이다
  (§macrumors-dev-forum-rules). 지금까지 못 쓰던 자리가 코드 100장으로 열린다.
- 페이지가 «iframe» 안에 그려진다 → 바깥 innerText 로 읽으면 빈 페이지로 보인다(실측 함정).

### A-2. 구독 오퍼 코드 — 만들 수 있다. 다만 **지우지 못한다**
- 구독 `com.signumhq.app.pro.monthly`(id **6786909663**) **APPROVED**, 판매 **175개국**, 기존 오퍼코드 **0개**.
- 엔드포인트 3개 모두 우리 키로 «쓰기 가능»함을 409 스키마 응답으로 확인:
  `subscriptionOfferCodes` · `subscriptionOfferCodeCustomCodes` · `subscriptionOfferCodeOneTimeUseCodes`
- **허용값(서버가 알려준 그대로)**
  · `duration`: THREE_DAYS · ONE_WEEK · TWO_WEEKS · **ONE_MONTH** · TWO_MONTHS · THREE_MONTHS · SIX_MONTHS · ONE_YEAR
  · `customerEligibilities`: **NEW · EXISTING · EXPIRED** (셋 다 넣으면 기존·만료 사용자도 쓸 수 있다)
  · `offerEligibility`: STACK_WITH_INTRO_OFFERS · REPLACE_INTRO_OFFERS
- ⚠ **`totalNumberOfCodes` 는 생성 때 넣을 수 없다**("can not be included in a 'CREATE' operation").
  수량은 «오퍼»가 아니라 **코드 발급(customCodes / oneTimeUseCodes)** 쪽에서 정해진다.
  → 5절의 「총 200장을 이렇게 나눈다」는 **오퍼 단위가 아니라 발급 단위**로 다시 읽어야 한다.
- ⚠ **`prices` 관계가 필수**다(무료 체험이어도). 지역 + 가격점을 inline 으로 같이 보내야 한다.
- ⚠ **DELETE 가 없다** — 허용 동작은 `CREATE, GET_INSTANCE, UPDATE` 뿐이다.
  한 번 만든 오퍼는 **끌 수는 있어도(active=false) 지울 수 없다.** 그래서 이름·조건을 처음에 맞게 넣어야 한다.
- **페이로드는 이미 검증했다.** 가격점만 일부러 가짜로 넣고 보냈더니 «가격점 id 형식» 하나만 걸렸다
  = 나머지(속성·구독 관계·prices 관계 모양)는 서버가 받아들인다. 승인 나면 그대로 보내면 된다.

## B. 구글 Play — 된다. 단 **대표가 약관을 눌러야 열린다**
Play Console → Monetize with Play → **Promo codes** 페이지 실측 문구:

> Give users a paid app, one-time product, or **subscription** for free.
> You can automatically generate **one-time codes**, or create your own **reusable custom codes**.

- ⚠ 1절에서 「맞춤 코드는 애플만」이라고 적었는데 **틀렸다. Play 도 재사용 맞춤 코드가 있다.**
- ⛔ **「Create promo code」를 누르면 «Promo codes 이용약관» 동의 창이 먼저 뜬다.**
  약관 동의는 내 안전선 밖이라 **취소로 닫았다**(누른 적 없음). **대표 클릭 1회가 필요하다.**
- 참고: Play 콘솔 실측 부수 확인 — 최근 28일 **평균 별점 5.00**, 총 사용자 5.

## C. ★가장 중요한 실측 — 「코드를 어떻게 쓰게 하느냐」가 진짜 병목이었다
- **앱 안에 «코드 사용» 입구가 없다.** 코드 검색 결과 `presentCodeRedemptionSheet` 호출이 앱 어디에도 없다.
  RevenueCat SDK(`@revenuecat/purchases-capacitor` 13.2.1)에는 그 함수가 **들어는 있다**
  (`dist/esm/definitions.d.ts:555`) — 화면에 연결만 안 돼 있다. 붙이려면 **빌드·심사**가 필요하다.
- 코드만 뿌리면 사용자는 스토어 앱을 열어 「기프트카드 또는 코드 사용」을 직접 찾아야 한다. 대부분 거기서 떨어진다.
- **빌드 없이 한 번에 여는 길을 실측했다:**
  · 애플 `apps.apple.com/redeem?ctx=offercodes&id=6783130444&code=X` → **302**, code·id 보존(데스크톱 웹도 열림)
  · Play `play.google.com/redeem?code=X` → **302** (`store/redeem` 은 **400**)
- → **오늘 배포했다**: `signumhq.com/app?from=<채널>&code=<코드>` 한 줄이면 두 스토어 모두 리딤 화면으로 간다.
  코드가 없으면 동작은 **이전과 완전히 같다**. 코드 링크 클릭은 `mkt:attr:code:<채널>:<날짜>` 로 **따로 센다**
  (일반 클릭과 섞으면 코드가 먹혔는지 채널별로 영영 못 잰다).

## D. ⚠ 4절 채널표 수정 — 「레딧에 «글»로 올린다」는 틀렸다
§reddit-posts-are-all-spam-filtered 실측: **우리 레딧 «글»은 전부 스팸필터에 죽는다**(작성자에게도 404).
사는 것은 **댓글**뿐이고, 댓글 본문에는 링크를 넣을 수 없다.
→ 레딧에서 코드를 쓰려면 **댓글에 코드 문자열만**(링크 없이) 넣고, 링크는 프로필로 가게 해야 한다.
그래서 순위를 다시 매긴다(건당 클릭·최근 3일 실측 기준):
