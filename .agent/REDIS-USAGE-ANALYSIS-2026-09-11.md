# Upstash Redis 사용량 분석 (2026-09-11)

대표 지시: 「전에 AWS 로 의존도를 줄였는데 사용량이 상당히 늘어난 것으로 보인다.
일시적인지 분석이 필요하다. 조정 가능한 부분, AWS 로 강화할 부분을 조사해라.」

**결론 먼저: 일시적이지 않다. 구조적이고, 이대로면 이번 달 예산을 넘는다.**

| 항목 | 값 |

| 명령 (9/1~9/11) | **1,020만** — 쓰기 4,728,484 / 읽기 5,475,761 |

→ **비용의 96%가 «명령 개수»다.** 대역폭·용량은 부차적이다.

정상적인 캐시는 읽기 9 : 쓰기 1 이다. 우리는 **5.5 : 4.7**.

### ★★ 미스율 약 70%
콘솔 Hits/Misses: 히트 ~2.5/s · **미스 ~6/s**. 캐시가 캐시로 작동하지 않고 있다.

## 2. 무엇이 때리는가 — Monitor 실측

02:36~02:38 ET(장 시작 전, 169초) 명령 324건을 키별로 집계했다.

| 키 패턴 | 비중 |
|---|---|
| **`intrinio:resp`** (벤더 응답 캐시) | **49%** |
| undercurrent:ticker | 11% |
| intrinio:snap | 8% |

### `intrinio:resp` 경로별 — GET 과 SETEX 가 «같다»
| 경로 | GET | SETEX | 현재 TTL | 접근 간격(중위) | 판정 |
|---|---|---|---|---|---|
| `securities/T/prices` | 105 (서로 다른 티커 **58개**) | | 120초 | 30~61초 | 최대 소비자 |
| `securities/T/prices/intervals` | 20 | **20** | 60초 | — | 미스율 100% |
| `securities/T/prices/realtime` | 41 | **28** | **10초** | **34초** | **TTL < 접근간격 → 구조적 100% 미스** |
| `indices/economic/…/level` | 10 | | **60초(기본값)** | **112초** | 월 단위 지표에 TTL 60초 |
| `companies/T` | 12 | 4 | 3600초 | 120초 | 정상 |

**키는 안정적이다**(`params={}`) — 「키가 매번 달라서」가 아니다.
실제 예:
```
QQQ/prices/realtime (TTL 10초)
  GET 15:36:27 → 미스 → SETEX
  GET 15:37:57 → 미스 → SETEX      ← 접근 간격 90초
```
**TTL 이 접근 간격보다 짧으면 캐시는 «절대» 히트하지 못한다.**
벤더 호출도 못 막으면서 Redis 명령만 2배로 쓴다(GET + SETEX).

## 3. 확정된 낭비 3건 (계산 가능)

### ① `market-feed` 가 자기 TTL 보다 10배 자주 쓴다  ★가장 큰 확정 낭비
- 스케줄 `* * * * *` — **24시간 매분, 주말 포함**
- 야후 심볼 **17개** × (읽기+쓰기 2명령) × 1,440분 = **하루 48,960 명령**
- 그런데 `setInCache(key, quote, 600)` — **TTL 이 600초(10분)다.**
  10분 유효한 값을 1분마다 덮어쓴다 → **9/10 이 낭비**
- `*/5` 로 바꾸면 9,792/일 → **하루 39,168 명령 절감 (월 약 $2.4)**
- 주말에도 매분 도는 것은 순수 낭비다(선물·암호화폐 외엔 값이 안 변한다)

### ② `indices/economic/*` TTL 이 60초
- BAMLH0A0HYM2(하이일드 스프레드)·PCEPI·T5YIE·CPIAUCSL — **월 단위로 갱신되는 지표**
- `vendorTtlSec()` 에 `indices/` 규칙이 없어 **기본값 60초**로 떨어진다
- 접근 간격 112초 > TTL 60초 → 매번 미스
- **6시간으로 올리면 거의 전부 히트.** 부작용 없음(값이 월 단위다)

### ③ `prices/realtime` TTL 10초 vs 접근 간격 34초
- 구조적으로 100% 미스 → GET+SETEX+벤더호출이 매번 발생
- 30초로 올리면 대부분 히트로 바뀐다
- ⚠️ 앱은 실시간 시세를 **WebSocket 오버레이**로 받는다(REST 는 폴백).
  화면 표시도 분 단위(`9/10, 11:52 ET`)라 30초 지연은 보이지 않는다

## 4. 가장 큰 기회 — MGET 배치 (아직 미확정)
- 169초에 **서로 다른 티커 58개**를 `securities/T/prices` 로 하나씩 GET 한다
- MGET 은 **N개 키를 1 명령으로** 읽는다 → 58 GET 이 2 MGET 이 된다
- 현재 MGET 사용량: 3시간에 **651회** (GET 은 94,000회) — 거의 안 쓰인다
- ⚠️ **아직 이 58개를 도는 호출부를 특정하지 못했다.** 그게 다음 작업이다
- ⚠️ 파이프라인은 명령 수를 줄이지 못할 가능성이 높다(Upstash 는 파이프라인 내
  개별 명령을 각각 센다). **MGET 만 확실하다** — 파이프라인 과금은 별도 확인 필요

## 5. 요금제 — Fixed 는 «명령 과금이 없다»
Upstash 문서 원문: *“Fixed plans have no command-count billing. You pay for data size,
bandwidth, and throughput limits, not per command.”*

| 플랜 | 가격 | 데이터 | 대역폭 | 명령 |
|---|---|---|---|---|
| Pay as You Go (현재) | $0.2/100K 명령 | 100 GB | 무제한 | 무제한 |
| **Fixed 250MB** | **$10/월** | 250 MB | **50 GB** | **무제한** |

**지금 당장은 안 맞는다**: 우리 대역폭 228 GB ≫ 50 GB, 데이터 220~236 MB 는
250 MB 한도에 이미 턱밑이다.
→ 3절 낭비를 걷어내 대역폭이 내려가면 재검토할 가치가 있다.
   상위 Fixed 등급(1GB/5GB/…)의 대역폭 한도는 **아직 확인 못 했다.**

## 6. AWS 로 강화할 부분
이미 `signum-unified-cache`(DynamoDB) 가 **Redis 미스 뒤 2차 캐시**로 7개 라우트에
붙어 있다(`src/lib/aws/unifiedCacheProvider.ts`). 패턴은 만들어져 있다.

**옮기기 좋은 후보** — 느리게 변하고 지연에 둔감한 것:
- `companies/*`(TTL 3600) · `fundamentals/*`(3600) · `prices/technicals/*`(600)
- `indices/economic/*` (월 단위)
DynamoDB 온디맨드 읽기는 Upstash 명령보다 **자릿수 단위로 싸다**(정확한 배수는
확인 필요). 이들은 «자주 읽히지만 거의 안 변하는» 자료라 Dynamo 에 가장 맞는다.

**옮기면 안 되는 것**: `prices/realtime`·`options/*` — 지연에 민감하고 TTL 이 짧다.

## 8. 실행 계획 — ★ 최우선 제약: 기능·체감은 절대 건드리지 않는다

대표 지시(2026-09-11): 「기능이나 체감에 문제가 생기는것은 절대로 안되는것이야」

그래서 **비용만 보고 TTL 을 올리는 안은 폐기한다.** 위험도로 3단계로 나눈다.
**1단계만 먼저 한다. 2·3단계는 «체감이 안 변한다»를 증명한 뒤에만 손댄다.**

### 1단계 — 체감 변화가 «수학적으로 0» 인 것만 (지금 해도 되는 것)

**1-A. 값이 안 바뀌었으면 쓰지 않는다 (market-feed)**
현재 `market-feed` 는 `getFromCache(key)` 로 이전 값을 읽고 나서
**비교 없이** `setInCache(key, quote, 600)` 한다.
→ 이전 값과 가격·타임스탬프가 같으면 **쓰기를 건너뛴다.**
- 화면에 나가는 값은 **완전히 동일하다**(같은 값을 다시 쓰는 것을 안 할 뿐)
- 미국 선물 휴장(금 17:00 ET ~ 일 18:00 ET, 주당 약 49시간) 동안은
  거의 모든 쓰기가 «같은 값 재기록» 이다 → 그 구간 쓰기가 대부분 사라진다
- **체감 영향 0. 갱신 주기도 그대로 매분이다.**

**1-B. `indices/economic/*` TTL 60초 → 6시간**
`vendorTtlSec()` 에 `indices/` 규칙이 없어 기본값 60초로 떨어지는 **설정 누락**이다.
- 대상: BAMLH0A0HYM2 · PCEPI · T5YIE · CPIAUCSL — **월 단위로 갱신되는 지표**
- 원자료가 한 달에 한 번 바뀌므로 **6시간 캐시해도 화면 값은 글자 하나 안 바뀐다**
- **체감 영향 0**

**1-C. MGET 배치 (호출부 특정 후)**
같은 값을 같은 시점에 읽되 명령만 합친다. **데이터·지연·화면 전부 동일.**
- ⚠️ 먼저 정규장 중 Monitor 재표집으로 58티커 호출부를 특정한다
- ⚠️ 파이프라인은 명령 수를 못 줄일 가능성이 높다 → **MGET 만** 쓴다

### 2단계 — 체감 영향이 «없음을 증명해야» 손대는 것
**2-A. `prices/realtime` TTL 10초 → 30초**
- 앱은 실시간 시세를 **WebSocket 오버레이**로 받고 REST 는 폴백이라는 것이
  코드상 사실이지만(`useIntelSharedDataForApp`), **화면별로 확인하지 않았다.**
- 증명 절차: ①WS 가 덮는 화면 목록을 코드로 확정 ②WS 없는 화면에서
  30초 지연이 실제로 보이는지 실기기/실화면 확인 ③둘 다 통과해야 적용
- **증명 전에는 손대지 않는다.**

**2-B. `market-feed` 스케줄 `* * * * *` → `*/5`**
- TTL 이 600초라 «캐시 관점»에선 낭비가 맞지만,
  **값의 나이가 최대 1분 → 최대 5분으로 늘어난다.** 상단 티커테이프의
  VIX·선물이 5분 낡아 보일 수 있다 → **체감 변화다.**
- 1-A(값 같으면 안 씀)만으로 휴장 구간 낭비가 사라지므로 **이 안은 보류한다.**
- 정 필요하면 «휴장 시간대만» 주기를 늘리는 방식으로 한정한다(값이 안 변하는 구간).

### 3단계 — 구조 변경 (한참 뒤)
- 느린 벤더 응답(`companies` 3600 · `fundamentals` · `technicals` 600 · economic)을
  **DynamoDB 2차 캐시로 이관**. 이미 `signum-unified-cache` 패턴이 있다.
  → 지연이 늘 수 있으므로 **화면별 응답시간 측정 후**에만.
- 대역폭이 50GB 아래로 내려가면 **Fixed 250MB($10/월, 명령 무제한)** 재검토.

### 검증 규칙 (무엇을 하든 공통)
1. 바꾸기 전/후로 **같은 화면을 실제로 열어** 값과 응답시간을 비교한다.
2. `npm run audit:screens` · `audit:ai` 로 29개 엔드포인트·AI 표면을 전수 확인한다.
3. 배포 후 Upstash 콘솔에서 **명령 수가 실제로 줄었는지** 24시간 뒤 재측정한다.
4. 하나라도 화면이 달라지면 **즉시 되돌린다.**

### 지금 당장 할 것 (대표 승인 대기)
1-A 와 1-B 는 체감 변화가 수학적으로 0 이라 바로 적용 가능하다.
1-C 는 정규장 중 재표집이 선행이다.
