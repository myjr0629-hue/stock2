## 0. 결론

  멈춰 있던 배경 요청(캐시 워머·LAST-GOOD 배경 갱신·미대기 쓰기)의 마감 타이머가 한꺼번에 울린다. 그 «가짜 타임아웃» 한 번이
  인스턴스 전체를 30초간 Upstash 로 돌렸다(래퍼 키는 Upstash 에 없어 미스 → 벤더 재계산).
- 수리 **v1**(`fix/redis-proxy-reliability-v1` = 18de82828, 관측 포함): **정체 감지 마감 + 차단기(5→30초·반개방) + 소켓 오류/정체 뒤 1회 재시도.**

## 2. 원인 — 메커니즘을 지목한 증거

1. **프록시 쪽 정체 없음** — 위 프로브·대조(9/9 사건에서 프록시 정상).
2. **타임아웃 난 요청의 «실제 경과»가 예산의 수십 배** — 관측 프리뷰 `[RedisStats]`(65 인스턴스·분): GET 타임아웃 경과 최대 **100,581ms**(예산 6초),
   같은 창 이벤트 루프 지연 최대 100,663ms. 2차(153 인스턴스·분): 최대 **242,972ms**.
3. **CPU 는 놀고 있었다** — 루프 5초+ 지연 창 191개 중 191개가 CPU 사용률 20% 미만(중앙 0.8%) → «과부하»가 아니라 «일시정지».
4. **옛 코드에서 재현** — `scripts/test-redis-reliability.ts` ②: 응답이 이미 도착한 상태에서 루프가 예산보다 오래 막히면
   옛 판(origin/main)은 응답을 버리고 «일시 중단(30초)» → Upstash. (libuv 다음 바퀴에서 timers 단계가 poll 보다 먼저 돈다.)
5. **되먹임** — 쿨다운 중엔 래퍼 키(`intrinio:resp:*`·`cache:*`…)가 Upstash 에 없어(9/18 정책) 미스 → 벤더 재계산 → 루프가 더 막힘.
   관측 프리뷰(약한 합성 부하)에서도 Redis 호출의 **27.8%가 Upstash, 그중 86.5%가 쿨다운·EC2 오류 사유**였다(운영 9/27 표본 «누수 39%»와 같은 모양).

## 7. 4단계(선택) — 큰 덩어리
`finra:offexchange`(2.19MB)는 메모 없이 프록시에서 직접 읽는다: `intrinio/fast`·`watchlist/batch` 호출마다 2회, `live/ticker` 미스마다 1회
(한 종목 행을 얻으려고 전체), 인텔 탭 하나가 분당 ≈40회. 작성 쪽이 JSON 문자열을 한 번 더 감싸 저장해 읽을 때마다 프록시가 ≈2.5MB 를
파싱·재직렬화하고 Vercel 은 두 번 파싱한다 — 인스턴스 루프를 막는 CPU 요인이기도 하다. **기능 동일** 해법: EC2 작업이 작은 버전 키
`finra:offexchange:ver` 를 함께 쓰고, 읽는 쪽은 버전이 같으면 인스턴스 메모를 쓴다(버전 키가 없으면 지금처럼 전체 읽기). EC2 작업 배포가
필요해 이번 브랜치에 넣지 않았다.

또 하나: `dashboard/unified` 모듈이 로드된 **모든 인스턴스**에서 90초마다 5종목 라이브 계산을 돌린다(`startCacheWarmer`, 운영 로그상
20~177초). 이 배경 작업이 일시정지 중 «떠 있는 요청»을 만드는 주 원인이다 — 기능(대시보드 신선도) 변경이라 별도 결정으로 남긴다.

  `vercel rollback` 또는 대시보드 Deployments → 직전 운영 배포 → «Instant Rollback».

- 되돌릴 기준(합친 뒤 3시간 장중, `node scripts/redis-stats-report.js --env production --since 3h`): 5xx 증가 · EC2 GET 실패율 1% 초과 ·
  쿨다운 시간 비중 1% 초과 · A/B 도구로 잰 운영 p50 이 기준선보다 유의하게 느림 — 하나라도 해당하면 되돌린다.
