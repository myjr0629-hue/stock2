# Redis 프록시 «가짜 타임아웃» 원인 수리 — 2026-09-29

> 대표 지시(9/29 00:0x KST): «Redis 개선 브랜치로 진행해 … 기능 성능저하가 발생해서는 전혀 안된다.»
> → 브랜치에서만 작업, 운영 배포 없음. 전후는 **같은 인프라(프리뷰)·같은 시각·무작위 순서의 A/B** 와 서버 내부 계측으로 비교했다.

## 0. 결론

- **프록시는 멀쩡했다.** 타임아웃의 원인은 Vercel 인스턴스 쪽이다: 응답을 보낸 뒤 **인스턴스가 일시정지**됐다가 다음 요청에 깨어나면
  멈춰 있던 배경 요청(캐시 워머·LAST-GOOD 배경 갱신·미대기 쓰기)의 마감 타이머가 한꺼번에 울린다. 그 «가짜 타임아웃» 한 번이
  인스턴스 전체를 30초간 Upstash 로 돌렸다(래퍼 키는 Upstash 에 없어 미스 → 벤더 재계산).
- 수리(`fix/redis-proxy-reliability`): **정체 감지 마감 + 차단기(5→30초·반개방) + 소켓 오류/정체 뒤 1회 재시도.**
  같은 부하에서 Redis 호출 중 Upstash 비중 **27.8% → 6.5%**, 쿨다운 시간 비중 **4.62% → 0.20%**, GET 실패 **1.22% → 0.37%**, SET 실패 **2.82% → 0.11%**.
- 응답 지연: 원본 대비 짝지은 차이 중앙값 **−1ms (95% CI −36~+53ms)**, p50·p95·p99 차이 모두 신뢰구간이 0 포함, 오류 0/0 — **저하 없음.**
- 중복 쓰기(3단계): 코드 전수 조사 결과 «독자 없는 유료 쓰기»는 이미 9/27 운영에서 끊은 `flow:ticker:lite:*` 하나뿐 — 새로 지울 것 없음(§6).

## 2. 원인 — 메커니즘을 지목한 증거

1. **프록시 쪽 정체 없음** — 위 프로브·대조(9/9 사건에서 프록시 정상).
2. **타임아웃 난 요청의 «실제 경과»가 예산의 수십 배** — 관측 프리뷰 `[RedisStats]`(65 인스턴스·분): GET 타임아웃 경과 최대 **100,581ms**(예산 6초),
   같은 창 이벤트 루프 지연 최대 100,663ms. 2차(153 인스턴스·분): 최대 **242,972ms**.
3. **CPU 는 놀고 있었다** — 루프 5초+ 지연 창 191개 중 191개가 CPU 사용률 20% 미만(중앙 0.8%) → «과부하»가 아니라 «일시정지».
4. **옛 코드에서 재현** — `scripts/test-redis-reliability.ts` ②: 응답이 이미 도착한 상태에서 루프가 예산보다 오래 막히면
   옛 판(origin/main)은 응답을 버리고 «일시 중단(30초)» → Upstash. (libuv 다음 바퀴에서 timers 단계가 poll 보다 먼저 돈다.)
5. **되먹임** — 쿨다운 중엔 래퍼 키(`intrinio:resp:*`·`cache:*`…)가 Upstash 에 없어(9/18 정책) 미스 → 벤더 재계산 → 루프가 더 막힘.
   관측 프리뷰(약한 합성 부하)에서도 Redis 호출의 **27.8%가 Upstash, 그중 86.5%가 쿨다운·EC2 오류 사유**였다(운영 9/27 표본 «누수 39%»와 같은 모양).

### 3-b. `fix/redis-proxy-reliability` — 원인 수리(관측 포함)
| 무엇 | 예전 | 지금 |
|---|---|---|
| 마감 | `AbortSignal.timeout(6000)` — 루프가 막혀도 그대로 끊음 | **정체 감지 마감**: 타이머가 250ms 넘게 늦게 울렸거나, 요청이 떠 있던 사이 100ms 심장박동이 정체를 봤으면 1.5초 한 번 유예 |
| 정체 뒤 실패 | 30초 차단 | 새로 1회 재시도, 그래도 실패면 **이 요청만** Upstash — 차단기는 안 연다 |
| 소켓 오류(fetch failed) | 30초 차단 | 지터 20~80ms 후 새로 1회 재시도(명령 전부 멱등, trade:* 서명은 시도마다 새로) |
| 차단기 | 첫 실패에 30초, 끝나면 동시 요청 «전부»가 다시 시도 | 진짜 실패에만 5·10·20·30초, 끝나면 **한 요청만** 시험(반개방) → 성공 시 닫힘·단계 초기화 |
| 쓰기 실패 | 로그 없이 Upstash | 그대로 Upstash(가용성) + 사유가 관측 줄에 남는다 |
| 응답 본문 | SET·DEL 은 본문을 안 읽음(소켓이 keep-alive 풀로 늦게 돌아감) | 끝까지 읽어 소켓을 바로 돌려준다 |
| 예산 | GET 6 · MGET 5 · SET 3 · DEL 3초 | **그대로** — 프록시 자체 p99.9(0.8초, 태평양 왕복 포함) 대비 충분. 줄이면 루프 경합으로 느려진 «정상» 응답을 끊을 위험만 커진다 |

**keep-alive**: Node 24 fetch(undici)는 이미 연결을 재사용한다. 별도 에이전트 대신 «본문을 끝까지 읽기»로 소켓 반환을 확실히 했다.

  `/api/admin/heartbeat` 의 Upstash 직접 쓰기(데스크톱 방문자마다 30초에 3명령, 독자는 관리자 위젯)를 ElastiCache 로 ·
  `gammaShieldEngine` 이 `structure:part:v2:*` 를 Upstash 에서 읽어 항상 미스(쓰기는 EC2 전용) ·
  교차섹터 브리프 v3(Lambda)·v4(Vercel) 같은 분 이중 생성.

## 7. 4단계(선택) — 큰 덩어리
`finra:offexchange`(2.19MB)는 메모 없이 프록시에서 직접 읽는다: `intrinio/fast`·`watchlist/batch` 호출마다 2회, `live/ticker` 미스마다 1회
(한 종목 행을 얻으려고 전체), 인텔 탭 하나가 분당 ≈40회. 작성 쪽이 JSON 문자열을 한 번 더 감싸 저장해 읽을 때마다 프록시가 ≈2.5MB 를
파싱·재직렬화하고 Vercel 은 두 번 파싱한다 — 인스턴스 루프를 막는 CPU 요인이기도 하다. **기능 동일** 해법: EC2 작업이 작은 버전 키
`finra:offexchange:ver` 를 함께 쓰고, 읽는 쪽은 버전이 같으면 인스턴스 메모를 쓴다(버전 키가 없으면 지금처럼 전체 읽기). EC2 작업 배포가
필요해 이번 브랜치에 넣지 않았다.

또 하나: `dashboard/unified` 모듈이 로드된 **모든 인스턴스**에서 90초마다 5종목 라이브 계산을 돌린다(`startCacheWarmer`, 운영 로그상
20~177초). 이 배경 작업이 일시정지 중 «떠 있는 요청»을 만드는 주 원인이다 — 기능(대시보드 신선도) 변경이라 별도 결정으로 남긴다.

## 8. 되돌리기
- 웹 코드만 바뀐다(EC2·Lambda·Redis 데이터 무변경). 합친 뒤 이상하면 **Vercel 즉시 롤백**(이전 운영 배포로 되돌림, 재빌드 없음):
  `vercel rollback` 또는 대시보드 Deployments → 직전 운영 배포 → «Instant Rollback».
- 저장소도 되돌리려면 합병 커밋을 revert: `git -C /tmp/stock2-main-merge fetch -q origin && git -C /tmp/stock2-main-merge reset -q --hard origin/main && git -C /tmp/stock2-main-merge revert -m 1 --no-edit <합병 커밋> && git -C /tmp/stock2-main-merge push -q origin HEAD:main`
- 되돌릴 기준(합친 뒤 3시간 장중, `node scripts/redis-stats-report.js --env production --since 3h`): 5xx 증가 · EC2 GET 실패율 1% 초과 ·
  쿨다운 시간 비중 1% 초과 · A/B 도구로 잰 운영 p50 이 기준선보다 유의하게 느림 — 하나라도 해당하면 되돌린다.
