## 1. ★ 가장 중요한 구분 — «축적/실시간»이 아니라 **«사실/판단»**

내가 처음에 "축적이 자산이니 12개월 뒤"라고 말했는데 **그건 판단 층에만 해당한다.**
대표 지적이 맞다 — **실시간으로 지금 쓸 수 있는 게 있다.**

| 층 | 예 | 검증 이력 | 지금 사용 |
|---|---|---|---|
| **사실** | 규모 6.2 지진(USGS·좌표·시각·원문) · 활동 중인 허리케인(NOAA) · NVDA 8-K 제출(SEC 원문) · 악용 중인 CVE(CISA) · GDACS 적색경보 · Kp 지수 · Polymarket 확률 | **불필요** | **✅ 오늘부터** |
| **판단** | 8축 종합점수(40/WATCH) · 사건→종목 영향점수·방향 | 필요 | ❌ 아직 |

**사실은 검증할 게 없다. 사실이니까.** 지진이 났다는 건 6개월 축적해야 믿는 게 아니다.
→ **사실 층은 오늘부터 자산이고, 판단 층만 시간을 기다린다.**

### 표현 규칙 (이게 지켜지면 컴플라이언스 문제 없음)
```
❌ "대만 지진 → NVDA 하락 위험"                                   ← 판단·예측
⭕ "대만에서 규모 6.2 지진 (USGS, 04:12 UTC).
    NVDA·삼성전자·SK하이닉스는 반도체 공급망 노출."               ← 사실 + 공개된 산업구조
```
두 번째는 **사실 진술 + 알려진 관계**다. 우리 앱 3개가 이미 쓰는 관찰형 어법 그대로.
**8축 점수·"경보"라는 단어는 아직 화면에 올리지 않는다.**

## 2. 소비 순서 — ★ 첫 소비처는 **쇼츠** (7월 판단에서 수정)

7월엔 SIGNUM, 8/1 1차 판단엔 WIM을 1순위로 봤으나 **즉시 착수 관점에서는 쇼츠가 맞다.**

| | 쇼츠 | WIM | UC | SIGNUM |
|---|---|---|---|---|
| 지금 상태 | 신규 라인, **사용자 없음** | **양대 스토어 심사 중** | 라이브(설치 0) | 라이브 |
| 데이터 오류 시 비용 | 영상 1편 재제작 | **라이브 앱에 오류 노출** | 앱 오류 | 앱 오류 |
| 이게 필요한가 | **정확히 필요** — `VIDEO_ENGINE_SPEC.md` §4-A "시장 전체 → 그 안의 종목" | 있으면 좋음 | 소재로 좋음 | 매크로 층 |
| 심사 리스크 | **없음** | 있음 | 있음 | 있음 |

**쇼츠 데일리 3편의 오프닝 컨텍스트가 정확히 "지금 세계에서 무슨 일이 있나"다.**
그게 없으면 우리 영상은 종목 얘기만 하게 된다. 사건 층이 들어가면 **세계 → 시장 → 종목** 구조가 완성된다.
읽기 전용·앱 무관이라 **실패 비용이 사실상 0.**

**순서: 쇼츠 → (WIM 스토어 승인 후) WIM → UC → SIGNUM**

### 각 소비처가 가져갈 것
- **쇼츠** — 사건 원장(오프닝 컨텍스트), 8축은 내부 참고용으로만
- **WIM** — `impact_edges` = "왜 움직였나"의 **출처 URL 붙은 후보**.
  지금 WIM은 AI 추론으로 원인을 만든다. USGS·SEC 원문 링크가 붙으면 교육 앱 신뢰도가 달라진다
- **UC** — 사건 원장 + SEC 원문 + 예측시장 = "뉴스≠돈" 포맷 소재. UC는 **차별화 소재가 부족**하다
- **SIGNUM** — 8축·거시 44항목을 Intel 매크로 층으로

## 3. 붙이는 방식 — 서버-서버만

핸드오프 §2: *"사이트가 소유자 전용이라 외부 Signum 앱이 곧바로 익명 호출할 수 있는 상태가 아니다."*
제시된 3안 중 **서버-서버**를 택한다.

```
Cloudflare Worker  →  우리 Vercel 서버  →  Redis 캐시(serveSWR)  →  앱
```
- 앱은 **우리 API만** 본다
- 공개 전환하면 rate limiting·abuse 방어를 새로 만들어야 함(§16이 지적)
- 권리 문제가 생기면 **우리 쪽 한 곳만 끄면 끝**

## 4. ⛔ 넣지 말아야 할 것 — 7월 리서치와 충돌하는 항목

### 4-A. 한국 시세(NAVER) — 라이브 앱에 붙이지 말 것
핸드오프 §15가 직접 경고: *"공식 개발자용 주식 API가 아니다. 유료 앱 전환 전 정식 공급자로 교체가 안전하다."*
**우리 앱은 이미 스토어에 있고 광고를 붙이는 중이다.** 비공식 스크래핑이 라이브 앱에 들어가면
리스크가 앱 전체로 번진다. → **미국 데이터·사건·거시만 쓴다.** 위 시너지는 그것만으로 다 성립한다.

### 4-B. 후보 목록 중 상업 이용 불가 — 7월 조사와 충돌
핸드오프 §14-A **후보 14번 OpenSky**가 올라 있으나, **7월 리서치 결론은 「상업 이용 금지」**다.
같은 문서에서 걸러낸 것:

| 소스 | 사유 |
|---|---|
| **OpenSky · adsb.fi** | 상업 이용 금지 |
| **ACLED** | 유료 + 대체물/AI 학습 금지 |
| **Kalshi** | 상업 표시에 서면 동의 필요 |

우리는 광고를 붙이는 **상업 서비스**다. "나중에 정리"가 아니라 **처음부터 안 넣는다.**

## 5. 소스 확장 — "최대한"이 아니다

소스마다 비용이 붙는다: 실패 표면 증가(지금도 22/29), **라이선스 확인 필요**(DB에 권리 메타데이터
없음 §15), rate limit. 소스가 많다고 신호가 늘지 않는다 — 노이즈가 는다.

### 실제로 채울 가치가 있는 구멍은 셋
| 우선 | 소스 | 메우는 구멍 |
|---|---|---|
| **1 ★** | **UCDP** | **지정학 분쟁 — 완전히 비어 있음**(§16-7). 8축 `physical`이 지진·태풍만 보고 전쟁을 못 본다 |
| 2 | NASA FIRMS | 산불 정밀 위치 (EONET보다 상세) |
| 3 | EIA | 에너지·원유 → 인플레이션 경로 |

**UCDP가 압도적 1순위.** 나머지는 있으면 좋은 정도.
그리고 **종목 확대는 급하지 않다** — §6 참조.

## 6. 되돌릴 수 있는 것 / 없는 것 — 이것이 우선순위를 정한다

| 나중에 채울 수 있음 | 지금 안 쌓으면 **영원히 없음** |
|---|---|
| 가격 (Polygon·Yahoo 과거 조회) | **사건 원장 — 무엇이 «언제 처음» 관측됐나** |
| 거시 시계열 (FRED가 과거를 다 준다) | **공급자 상태·지연** |
| 12개 → 전체 종목 확대 | **"그 시점에 알 수 있었나"의 증거** |

→ **12개 자산이 좁은 건 생각보다 문제가 아니다.** 가격은 나중에 채워진다.
→ **진짜 왕관은 사건 원장이다.** "8월 1일 11시 25분에 처음 봤다"는 기록은 어디서도 살 수 없다.
→ 확장은 **종목보다 사건 소스**가 우선.

### 축적 설계는 이미 «나중에 재계산 가능»하게 되어 있다 (중요)
축적 전략의 최대 위험은 *"나중에 기준이 바뀌면 쌓아둔 게 무의미해지는 것"*인데, 이건 피해 뒀다.

| 설계 | 효과 |
|---|---|
| `risk_evaluations`에 판정뿐 아니라 **원가격 + 이후 가격** 저장 | 검증 규칙이 바뀌어도 **과거 데이터로 재채점 가능** |
| `impact_edges`에 `ruleVersion`, *"이전 결과를 덮어쓰지 않는다"*(§19-9) | 규칙 세대별 성능 비교 가능 |
| 사건에 `firstSeenAt`/`lastSeenAt`/`observedCount` 분리 | **리드타임** 측정 가능 |

현재 검증 규칙은 조악하다(위험≥55 → 수익률 음수면 일치; 베타·휴장·이벤트종류 무시, §10이 자인).
**그래도 원자료가 남아 지금 쌓아도 손해가 없다.** 코덱스의 "일단 축적" 판단이 맞는 이유가 이것.

## 7. 지금 당장 해야 할 단 하나 — **죽으면 알게 하기**

축적 시스템은 요란하게 죽지 않는다. 공급자가 응답 형식을 바꾸거나 Worker가 죽으면 **아무 일도
일어나지 않고**, 3개월 뒤 "구멍이 3개월"인 걸 발견한다. **그 3개월은 못 되돌린다.**

`source_observations`에 run마다 공급자 성공·실패가 이미 저장된다. **읽어서 알려주는 것 하나**면 된다.
- 마지막 스냅샷이 N분 이상 없으면 알림
- 정상 공급자 수가 기준치 아래로 떨어지면 알림

**30번째 소스를 붙이는 것보다 이게 먼저다.**
(핸드오프 §12: cron 미설정 시 축적이 «페이지 호출 시»에만 발생 → 대표 확인 결과 별도 프로젝트에서
축적 중. 그렇다면 남은 위험은 «켜져 있다고 믿는데 비어 있는 것» 하나뿐이다.)

## 8. 단독 제품으로서 — 지금은 아니다

| 형태 | 판정 |
|---|---|
| B2C 매크로 대시보드 | ❌ 데이터가 전부 무료·공개 = 해자 없음. 시장 포화. 게다가 구독료를 받으면 "예측한다"는 주장을 하게 되고, §8이 스스로 *"위기를 예측한다고 단정하면 안 된다"*고 경고한다. 그 선을 넘으면 규제·평판 리스크가 **앱 3개 전체로 번진다** |
| **검증 이력 데이터셋/API** | ⭕ **12개월 축적 후.** 단독으로 성립하는 유일한 형태 |
| 포트폴리오·기술 증명 | ⭕ 이미 성립 |

**단독으로 팔 수 있는 유일한 물건:**
> "사건이 있었다 → 이 종목에 영향 → 실제로 1시간/1일/7일 뒤 이렇게 됐다"를 **전부 기록해둔 DB**

대부분의 대시보드는 **지금**만 보여주고 자기 예측을 기록하지 않는다. 틀린 게 남으니까.
**우리는 남긴다. 그게 유일한 차별점이다.**

### 코덱스의 "공급처가 된다" — 맞다. 다만 첫 고객은 외부가 아니다
```
1순위 고객   우리 앱 4개 + 쇼츠   ← 확실함, 지금부터
2순위        외부 API 판매        ← 12개월 뒤 가능성
```
외부 판매는 "될 수도 있는 일"이지만, **쇼츠에 사건 컨텍스트를 먹이고 WIM에 출처 있는 정답을
주는 건 지금도 확실한 가치**다. 공급처 개념은 유지하되 **첫 납품처를 우리로 잡으면 12개월을
기다릴 필요가 없다.**

## 10. 결론 5줄

1. **사실 층은 오늘부터 쓸 수 있다.** 판단 층(8축·영향점수)만 축적을 기다린다
2. **첫 소비처는 쇼츠** — 필요가 정확히 맞고, 심사 리스크 0, 실패 비용 0
3. **붙이는 방식은 서버-서버**, 한국 시세(NAVER)·OpenSky·ACLED·Kalshi는 **제외**
4. **소스 확장은 UCDP 하나가 진짜.** 그전에 «죽으면 알게 하기»가 먼저
5. **단독 제품화는 하지 않는다.** 켜두고 재우는 자산이지 지금 꺼내 파는 자산이 아니다
