# IBM Command VWAP 장외 결측 수리

## 결과 요약

조사 원문 `ibm-command-vwap-blank.md`를 끝까지 읽고 코드에서 다음 원인을 확인했다.
장외에는 분봉·완료 세션 보관본이 모두 없으면 자체 분봉 조회가 없었고, 빈 응답도 60초 캐시에 들어갔다.
장외 날짜 검사와 마지막 정상본 병합에서도 다른 기준일 값이 통과할 수 있었다.

목표 정규장 날짜는 기존 거래소 달력의 `shownRegularSessionDate`로 정한다.
개장 전·주말·휴장은 직전 완료 세션, 정규장 진행 중·마감 뒤는 해당 거래일이다.
그 날짜의 봉만 기존 `sessionVwapFromBars` 산식으로 계산한다.
차트·날짜별 복구 분봉·같은 날짜의 보관본에 자료가 없으면 기존 분봉 조회·세션 분류 함수를 재사용해 해당 하루만 조회한다.
종목·날짜별 60초 원자적 잠금과 인스턴스 내 진행 중 요청 합류로 중복 조회를 막는다.

빈 VWAP 응답 TTL은 5초다. 이미 저장된 빈 응답이나 다른 날짜 값에 캐시가 적중하면 동일 세션 자료를 재확인한다.
마지막 정상본 병합 뒤와 최종 응답 출구에서도 날짜를 검사한다.
스냅샷 경로도 원천 정규장 날짜가 확인된 값만 사용한다.
화면·라벨·문구는 수정하지 않았다.

## 바꾼 파일

- `src/app/api/live/ticker/route.ts`: 목표 날짜 선택, 동일 세션 조회·복구, 캐시 적중 재확인, 빈 응답 TTL, 병합 후 날짜 검사.
- `src/services/stockApi.ts`: `getRegularSessionMinuteBars` 추가. 기존 `getAggregates`·`maskOneDaySessions` 재사용.
- `tests/tickerVwapColdCache.test.js`: 실제 라우트와 분봉 함수를 실행하는 오프라인 회귀 시험.
- 이 보고서.

공유 함수의 기존 구현·인자는 변경하지 않았다. 추가 분봉 함수의 운영 호출자는 ticker 라우트 한 곳이다.
라우트 내 날짜 검사의 호출자는 캐시 적중·마지막 정상본 병합·최종 응답 출구이며 모두 시험했다.
앱 Command의 기본/`chain=0`, 웹 등 `skip_alpha=1`, `chain=full`을 포함한 네 응답 모양에 같은 수리가 적용된다.
복구 분봉은 별도 날짜 키에 보관하므로 화면용 차트 캐시의 PRE·POST 자료를 덮지 않는다.

## 남은 위험

위 결과는 오프라인 모형 실측이며 운영 IBM 응답을 확인한 결과는 아니다.
공급사가 목표 날짜 자료를 주지 않거나 잠금 저장소가 실패하면 값은 여전히 비어 있을 수 있다.
이때 다른 날짜 값으로 메우지 않으며, 공급사 재조회는 종목·날짜별 잠금 만료 뒤 가능하다.
다른 인스턴스의 조회가 늦으면 자료 재확인 대기 5초와 저장소 I/O 시간이 첫 요청 지연에 더해질 수 있다.
운영 데이터 쓰기·push·main 병합·배포는 실행하지 않았다.
브랜치 `fix/ticker-vwap-cold-cache`에서 커밋을 준비했으나 `git add`의 작업공간 `index.lock` 생성이 `Operation not permitted`로 차단됐다. 커밋은 아직 없다. 수정 파일은 디스크에 저장돼 있다.
